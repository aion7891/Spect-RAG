## Phase 1: code and mathematical audit

### How the audit was done

1. Every module was re-read against the paper (Eq. 3, 10–13, 17–27; Tables 1–2; Algorithm 1).
   Phases 2–6 had already been reviewed once; this pass also covered seeding, expansion,
   diffusion, selection, prompt building, metrics and evaluation.
2. The real pipeline was profiled with `cProfile` on the **full MultiHopRAG corpus** (609 news
   articles, 1.06 M words → 10,335 chunks of 256 tokens), the dataset used in Phase 3.
3. Each fix was checked by tests. Each vectorised rewrite was checked against the original
   loop version for **identical** output (`tests/test_equivalence.py`).

### Findings and fixes

| # | Finding | Kind | Fix |
|---|---|---|---|
| 1 | `save_index` took **53%** of ingestion: 2.9 M raw signal edges written as indented JSON | Performance | Edges and signals saved as binary `.npy` / `.npz`; chunks as compact JSON. Old JSON indexes still load |
| 2 | **2.79 M entity edges** on 10k chunks: the regex extractor produced fragments (`u`, `s` from "U.S."), months, weekdays and "new"; common names below the 5% cap still linked hundreds of chunks | Correctness and performance | One-letter fragments and months/weekdays/"new" removed; cap lowered to 1% of chunks (≥ 20); entity and section signals keep each chunk's `graph_k` strongest edges → **69,570** entity edges |
| 3 | Graph walk used Python dicts (4.9 M lookups per 300 queries) and fully sorted every layer; hop 2 was computed even when hop 1 already filled the 200-candidate cap | Performance | Graph stored once as CSR arrays; the walk uses numpy; it stops when the cap is reached |
| 4 | RRF, rankings and the "has questions" mask looped over all chunks in Python for every query | Performance | Vectorised (`np.argsort`, `np.lexsort`, array RRF) with the same tie order |
| 5 | BM25 scoring looped over every posting in Python | Performance | Postings stored as numpy arrays; one vectorised update per query word |
| 6 | Greedy selection evaluated Eq. 21 one candidate at a time, and `k not in picked` scanned a list | Performance | Eq. 21 computed for all candidates at once (numpy); a boolean mask for picked candidates |
| 7 | `hash_embed` recomputed md5 1.6 M times (its cache lasted for one call only) | Performance | Module-level `functools.lru_cache` |
| 8 | Retrieval loaded the raw signals, which it never uses | Memory | `load_index(..., skip=("signals",))` |
| 9 | `ingest()` only accepted files | Usability | New `ingest_documents(docs)` for documents already in memory |

### Mathematics verified

| Check | Result |
|---|---|
| Eigenpairs on the real 10,335-node graph (sparse `eigsh` path) | max ‖L u − λ u‖ = **5.6e-15**; U orthonormal; orthogonal to the trivial `√degree` vector (max \|uᵀu₁\| = 5.2e-15); λ₂ = 0.0108 > 0 (the graph is connected) |
| Personalized PageRank (Eq. 18) | equals the closed form β(I − (1−β)Ã)⁻¹r (existing test) |
| Sparse vs dense eigensolver | same eigenvalues to 1e-6 (existing test) |
| Spectral closeness and clustering under eigenvector sign flips | invariant: flipping the sign of coordinate k flips both the candidate and the seed centre, so the cosine is unchanged; k-means on row-normalised points mirrors |
| Vectorised expansion, RRF/top-seeds, BM25, selection vs the original loops | **identical** results on 71 random cases with deliberate ties |
| BM25 vs a from-scratch implementation of the formula | equal (`test_bm25_matches_reference`) |

No mathematical errors were found in Eq. 3, 10–13, 18, 21–22 or the Section 4.5 metrics. The
problems were efficiency and entity-extraction noise.

## Phase 2: algorithm improvements

### What was added

| Area | Setting / API | What it does |
|---|---|---|
| Selectors (Section 3.8, Table 3) | `selector` = `spectrag` (default), `mmr`, `protected_mmr`, `anchor_expand_ce`, `topk` | `mmr`: Maximal Marginal Relevance under the token budget, `mmr_lambda` (0.7) weighs relevance against novelty. `protected_mmr`: the protected core first, then MMR. `anchor_expand_ce`: anchors, then the anchors' graph neighbours ranked by a cross-encoder (`rerank_fn`) or by score, then backfill. `topk`: score order (ablation) |
| Proximity (Section 3.7, Table 2) | `proximity_mode` = `hybrid` (default), `ppr`, `spectral`, `heat`, `none` | `heat` is Eq. 17, `exp(−tL)s`, computed from the stored eigenpairs (trivial `√degree` vector + `U e^(−tΛ) Uᵀ s`) |
| Per-call settings | `search(q, settings={...})`, `retrieve(q, settings, query_vector=...)` | Any retrieval setting can change per query; precomputed query vectors avoid re-embedding in benchmarks |
| Graph settings without re-embedding | `SpectRAGRetrieval(dir, {"edge_threshold": 0.1})` or `search.rebuild_graph({...})` | Re-fuses the saved signals (Eq. 10) and recomputes the spectral coordinates and clusters (Eq. 11–13). A per-call graph change raises a clear error |
| Tuning | `spectrag.utils.tuning.tune(search, questions, grid, objective, budget, trials)` | Grid or random search over any settings on validation questions; graph rebuilds are grouped; the search object is restored afterwards |
| Vector search (Section 6.2) | `ann_backend` = `auto` (default), `exact`, `faiss`, `hnsw`; `hnsw_m`, `hnsw_ef_construction`, `hnsw_ef_search`, `dense_top_n` | Used for the semantic kNN graph at ingestion and for dense seeding at query time. `auto` = exact up to 20,000 chunks. FAISS/HNSW indexes are saved with the index (`vectors.faiss` / `vectors.hnsw`) |
| Refactor | `utils/graph_build.py` | Graph and spectral building shared by ingestion, `rebuild_graph()` and tuning |

### Verified

| Check | Result |
|---|---|
| `heat` proximity vs `scipy.linalg.expm(−tL) s` with the full eigenbasis | equal (`test_heat_diffusion_equals_matrix_exponential`) |
| `rebuild_graph(edge_threshold=0.12)` vs ingesting with `edge_threshold=0.12` | **identical** edges and spectral coordinates |
| Exact top-k search vs brute force | identical ids and scores |
| FAISS / HNSW top-10 recall vs exact (2,000 random vectors) | ≥ 0.95; saved and loaded indexes give the same results |
| Every selector on random cases | never exceeds the budget, no duplicates |
| MMR with `mmr_lambda = 1` | equals top-k (as the formula requires) |

### ANN benchmark (`python benchmarks/ann_benchmark.py`, clustered synthetic 768-d vectors, k = 10)

Results are in `benchmarks/results/ann.md` and `ann.json` (Apple Silicon Mac, Python 3.14).

| Chunks | Backend | kNN graph build (s) | Edge recall vs exact | Query top-1000 (ms) | Top-1000 recall |
|---|---|---|---|---|---|
| 10,000 | exact | 0.77 | 1.000 | 0.117 | 1.000 |
| 10,000 | faiss | 1.09 | 1.000 | 0.224 | 0.992 |
| 10,000 | hnsw | 2.43 | 1.000 | 0.346 | 0.993 |
| 50,000 | exact | 17.81 | 1.000 | 0.439 | 1.000 |
| 50,000 | faiss | 6.04 | 1.000 | 0.383 | 0.884 |
| 50,000 | hnsw | 10.8 | 1.000 | 0.539 | 0.884 |
| 100,000 | exact | 70.92 | 1.000 | 0.884 | 1.000 |
| 100,000 | faiss | **10.43** | 1.000 | 0.322 | 0.831 |
| 100,000 | hnsw | 18.27 | 1.000 | 0.394 | 0.830 |

What this means:

- **Ingestion:** at 100k chunks FAISS builds the semantic graph **6.8× faster** with the same
  neighbours (edge recall 1.000). Exact is `O(n²)`: 0.8 s → 17.8 s → 70.9 s.
- **Query time:** exact numpy search is already below 1 ms at 100k chunks, and the approximate
  top-1000 list loses 12–17% of its tail at 50k–100k. So `auto` keeps exact search up to 20,000
  chunks; approximate search pays off for much larger collections, or when memory for the full
  matrix product is the limit.
- These are synthetic vectors. Phase 3 measures the backends on real nomic-embed-text
  embeddings of MultiHopRAG.

## Phase 3: MultiHopRAG benchmark (quick mode)

Full report with every table and both charts: `benchmarks/results/multihoprag/REPORT.md`.
Raw per-question results: `benchmarks/results/multihoprag/*.json`.

### Setup

- **Data:** MultiHopRAG, 609 articles; 2,255 questions with evidence (null questions excluded),
  split once with a fixed seed into **300 validation** (tuning only) and **1,955 test** (all reported numbers).
- **Index:** `nomic-embed-text` via Ollama, 1,200-token max chunks with 100 overlap (paper Table 1)
  → 7,807 chunks (semantic chunking makes chunks shorter than the maximum), 56,390 graph edges, 39.5 MB.
- **Budget:** 12,000 tokens for **every** method (paper Table 2).
- **Gold:** a chunk of the evidence's own article that contains the fact word for word; 13 facts
  crossing a chunk boundary use a half-fact fallback.
- **Quick mode:** at your request this phase was cut from hours to minutes, which means one chunk
  setting, 30 tuning trials, and small LLM samples. `SPECTRAG_BENCH_FULL=1` runs the full version.
  Quick mode also finds semantic-chunking breaks with the offline hash embedder (new setting
  `semantic_embedder`), because embedding about 60,000 sentences through Ollama took over an hour.

### Retrieval, 1,955 test questions

| Method | Recall@5 | Recall@10 | Evidence recall (budget) | All evidence found | MRR |
|---|---|---|---|---|---|
| Standard RAG (dense top-k) | 0.355 | 0.483 | 0.758 | 0.512 | 0.507 |
| BM25 top-k | 0.462 | 0.577 | 0.788 | 0.545 | 0.617 |
| Dense + MMR | 0.359 | 0.482 | 0.756 | 0.507 | 0.508 |
| Hybrid RAG (dense + BM25, RRF) | 0.445 | 0.574 | 0.832 | 0.615 | 0.609 |
| SpectRAG, default settings | 0.385 | 0.433 | 0.803 | 0.550 | 0.592 |
| **SpectRAG, tuned on validation** | **0.470** | **0.592** | **0.846** | **0.639** | **0.617** |

Paired bootstrap, tuned SpectRAG − hybrid: evidence recall **+0.014** (95% CI +0.007 … +0.021),
Recall@10 **+0.017** (+0.009 … +0.025). Tuned SpectRAG − standard RAG: +0.088 and +0.109.
By question type, the largest gain is on **inference** questions (0.802 vs hybrid 0.757); on
comparison questions hybrid is slightly ahead (0.911 vs 0.902), as in the paper.

Tuned settings (best of 30 trials on validation, validation recall 0.794 → 0.841):
`alpha 0.3, precision_floor 0.2, seed_count 20, selector protected_mmr, proximity hybrid,
bm25_weight 0.7, edge_threshold 0.05, graph_k 5`.

**Finding about the defaults.** The default selector (paper Eq. 21–22 with the guessed `ρ = 0.5`)
favours very short chunks: it picks 85 chunks where other methods pick about 47, and its Recall@10
falls to 0.433. With `length_power = 0` its Recall@10 rises to 0.580. `topk` and `mmr` selectors on
SpectRAG's graph-re-scored candidates reach 0.845 evidence recall without any tuning. Ablations:
no graph expansion 0.705 (this also shrinks the candidate pool); heat-kernel proximity 0.732.

### Fixes made during the benchmark

- `ollama_llm()` never set `num_ctx`, so Ollama silently cut long (12k-token) prompts: it is now
  sized to the prompt.
- Ollama calls (LLM and embedder) had no retries; one slow call aborted a run: 2 retries, then a
  clear `ConnectionError`.
- New `max_tokens` option for `ollama_llm()`; new `semantic_embedder` setting.
